The 8 foundational decisions

These are the rules every component inherits. Locking them once — with values you can see — means the ~100-component polish becomes mechanical instead of re-argued each time. Each one below: what it means in plain terms, the proposed decision, and where useful, the real thing rendered. Toggle dark (top-right) to check both themes.

A

Wash tokens

Plain version: when a surface needs to say "this is a success / error / warning / note," we tint it a whisper of that color instead of drawing a colored stripe or a loud fill. A "wash" is that whisper — the status color pulled ~26% of the way over the page background, so it reads as "tinted" not "shouting." One recipe, used everywhere, so an alert, a toast, and an AI block all feel like one family.

Locked

Wash = status-2, the DS "Subtle background" step, as authored. No new tokens, no mixing — the rail-replacement surfaces (toast error, block low-confidence, calendar, chat-internal) reuse bg-{status}-2. Green/blue read as quiet tints by design; amber runs a touch warmer (it's authored hotter) and that's fine. Use-cases below render at step-2.

B

Motion contract

Plain version: two problems. (1) Lots of our animations overshoot — they bounce past their spot and settle back, which is the springy, toy-like "AI motion" feel. (2) Some looping animations (a pulsing dot, a spinning icon) don't stop for people who set "reduce motion" in their OS, which can trigger nausea. The fix: things settle instead of bounce, and every animation checks the reduce-motion setting.

Decision

Settle, don't bounce, by default. Keep a springs.bouncy token but use it only where overshoot is intentional (a celebratory success). Every animated component reads useReducedMotion() itself so it's correct standalone. Click the chips — same press, two personalities:

If your OS has "reduce motion" on, the pulse above is already static — that's the behavior we want on every loop.

C

Controlled / uncontrolled contract

Plain version: some components (a dropdown, a date picker) hold a value. Two ways to use them: let the component remember its own value ("uncontrolled" — you just drop it in), or you hold the value and tell it what to show ("controlled" — needed for forms). Right now ~24 components only support the second, and many named their "value changed" callback differently (onChange, onSelect, selectedId…), so learning one doesn't help with the next.

Decision

Every stateful component supports both modes via one shared helper, with one naming rule: value + defaultValue + onValueChange (and open/defaultOpen/onOpenChange). No visual — it's an API rule.

today — inconsistent

// each component different, controlled-only
<Combobox selectedId={id} onSelect={setId} />
<DatePicker value={d} onChange={setD} />
// no way to just drop one in uncontrolled

after — one contract

// uncontrolled — component remembers
<Combobox defaultValue={id} />
// controlled — you hold it, one handler name
<Combobox value={id} onValueChange={setId} />
D

Slots over corner-props

owned by cards workstream

Plain version: when a component needs "something in the corner" (a button, a badge, an icon), there are two API styles. The corner-prop way bakes in a named hole (action=, badge=, headerRight=) — every new need is a new prop, and you can only put what the author imagined. The slot way (what Card's <CardAction> does) lets you drop any child in that region. Slots scale; corner-props sprawl.

Decision

Card's slot model is the DS law. New composition goes through slots; the bespoke corner-props (avatar badge, banner actions, popover title, stat-card footer, …) get @deprecated and removed at the clean-break release. Same rendered result, open-ended API:

corner-prop — closed

<Card
  headerActions={<IconButton/>}
  badge="New"
/>
// want two buttons? a menu? — can't

slot — open

<Card>
  <CardAction pos="top-right">
    <Badge>New</Badge>
  </CardAction>
  // any children, any count
</Card>
E

Variant / color vocabulary

Plain version: every component should describe itself with the same words. Emphasis is variant (solid / soft / outline / ghost / link), size is size (xs–xl), meaning is color (accent / neutral / success / warning / error / info). Today some components invent their own (padding="spacious", display="full", status=, variant="light|dark") and one legacy value — color="default" — even lives in Card itself and duplicates neutral.

Decision

Canonical variant / size / color axes everywhere; off-taxonomy axes renamed at the clean-break; color="default" removed in favor of neutral. The emphasis ladder (accent shown):

F

Surface & radius family

Plain version: a card should be lifted off the page by a soft shadow (elevation), not boxed in by a 1px border — and never both at once (border + shadow together is a classic AI tell). Some of our skeleton/loading tiles use a border and the wrong, too-round corner (the Dialog radius) so they don't match real Cards. Pick one card look and share it.

Decision

Cards & card-like tiles are elevation-led (shadow-raised, rounded-surface 10px) — no 1px border. Border-led (outline variant) is a deliberate opt-in, never the default. Same content, two treatments:

G

Touch targets — 44px

decided — opt-in

Plain version: anything you tap (a close ✕, a nav arrow, a small icon button) should have a hittable area of ~44×44px on touch, even if the icon is tiny (a WCAG rule). But forcing that globally would reflow the tight, dense layouts already shipping in Karm. So we grow the invisible tap area, not the visible box — and let the consumer turn it on where it matters.

Decided

Hit-area, not footprint — and toggleable. A touch-target utility expands the tap area to 44px via an invisible overlay (::before / negative-margin), so the control's visual size and layout are unchanged. It's opt-in (utility class / prop / a provider flag) so consumers enable it in touch contexts and leave dense desktop toolbars alone. Dashed = the expanded tap area; the glyph box doesn't move:

H

State-coverage convention

Plain version: a component isn't "done" when the happy path looks nice. It has to survive dark mode, Windows high-contrast mode, right-to-left languages (Arabic/Urdu — icons must mirror), reduced-motion, and the empty/loading/error/disabled states. Today almost none of our stories or tests check those, so regressions slip through. This is a testing/story habit, not a visual choice.

Decision

A shared describeA11yStates test helper + a stories convention so every component demonstrates the same checklist. What "covered" means:

defaulthoverfocus-visibledisabled loadingerroremptydark forced-colorsRTLreduced-motion

Not every state applies to every component — but the helper makes the applicable ones non-optional.
