**Date**: 2026-08-18
**Status**: decisions locked, Phase 1 not started
**Figma file**: `bcBO7RgVYR4ulwPr3j2heY` — "Shilp Sutra DS" (empty at time of writing)
**Supersedes**: `2026-04-20-figma-port-design.md` (wrong file, unbuildable variant counts, Code Connect plan our account cannot use)

## Why this document replaces the April plan

The April plan targeted a different Figma file (`diyRzIcyZUXsmwrBlsyAJl`), proposed a 600-variant Button that undercounted the size axis (the real product is 1,200), and planned around Code Connect. Three things were established by measurement this time rather than assumption:

1. **Figma's own stated ceiling**: components with more than 1,000 variants may hit performance problems. And a consuming file imports *every* variant of any component set it touches — so the cost lands in designers' mockup files, not ours.
2. **Reference libraries measured directly** (imported via MCP, read their real matrices): Material 3 `Button` = 50 variants, M3 `Icon button` = 150, Figma's Simple DS `Button Danger` = 12. Neither crosses intent with style inside one set. Nobody ships anything near 1,100.
3. **Our plan tier is Pro** (`whoami`): Code Connect requires Organization/Enterprise. It is blocked, not deferred. Variable mode ceiling measured empirically at **10 per collection** (`"in addMode: Limited to 10 modes only"`).

The April plan treated variants as the only lever. The decisive correction: **Figma variable modes can carry a whole axis at zero variant cost.** Proven with a working spike before committing (see Decision 3).

## Decisions

### D1 — Split authority: Figma owns token *values*, code owns *structure*

**Amended 2026-08-18.** The April position ("Figma consumes; it does not dictate") no longer holds for tokens.

| | Source of truth | Flows |
|---|---|---|
| **Token values** — ramp seeds, semantic alias targets | **Figma** | Figma → code, via `figma-pull-tokens.mjs` → PR |
| Token *structure* — which tokens exist, their names, scopes | Code | code → Figma |
| Components — props, variants, behaviour | Code | code → Figma |

This is **ongoing**, not a one-off pass: designers decide the palette and the role mappings, permanently. Everything else still flows code → Figma.

The split works because of a strict limit on what "tuning" means (D13). Without that limit, Figma-as-source-of-truth would degrade the system, since Figma has no OKLCH and round-tripping colour through sRGB is lossy.

### D13 — Tuning means seeds and re-pointing. Never hand-edited steps.

Exactly two operations are in scope:

```
1. SEED       adjust a ramp's hue, peak chroma and contrast corrections
                                                 →  all 12 steps regenerate, evenly spaced
2. RE-POINT   change which step a semantic token aliases to
              surface/raised → neutral/1   becomes   surface/raised → neutral/2
```

**A seed is five numbers, not two** — `hue`, `peakChroma`, and corrections for `light9`, `dark9`, `dark10`.

Found while building the regenerator: steps 9 and 10 are the solid fills that carry text, and the generic lightness curve does not clear WCAG for every hue. Five ramps carry hand-applied corrections — exactly the ones backing semantic intents:

```
corrected:  pink (accent) · red (error) · green (success) · blue (info) · neutral
untouched:  purple yellow teal amber slate indigo cyan orange emerald
```

`generate-scale.ts` did not model these, which meant **it could not reproduce the palette it supposedly generates** — regenerating any of those five silently reverted the contrast fix. Now modelled as an optional `correction` on `ScaleOptions`, verified at 336/336 by `figma-plugin/verify-parity.mjs`.

**Why the limit matters.** The ramps are generated by `src/tokens/generate-scale.ts` from a hue and a peak chroma, in OKLCH, which is what makes the 12 lightness steps perceptually even. Figma has no OKLCH; designers pick in sRGB. Hand-setting an individual step overrides a mathematical system with an eyeballed value and breaks the evenness of the ramp.

**And it makes the port back lossless.** OKLCH → sRGB *clips* anything outside the sRGB gamut, so a naive pull would rewrite colours nobody touched, permanently baking in the clipped version. Seeds are two numbers per ramp. Re-pointing is a pure reference change with no colour conversion at all. Neither loses information.

Individual-step editing is **out of scope**. If a generated step is genuinely wrong, that is a seed problem or a scale-generator problem, and it gets fixed in code.

### D14 — `figma-pull-tokens.mjs` consumes a plugin export and opens a PR

**Built 2026-08-18.** One constraint reshaped it: the Variables REST API is available only to "full members of Enterprise orgs", for both read and write (verified against Figma's docs). Devalok is on Pro, so **no standalone script can read the Figma file**. The path is:

```
Figma  →  plugin "Export tokens as JSON"  →  save  →  figma-pull-tokens.mjs  →  PR
```

Tested both directions: an unchanged export reports no changes and exits 0; an export with three perturbed seeds and one re-point reports exactly those four and exits 1.

Requirements:

- Reads ramp seeds and semantic alias targets from Figma; writes `primitives.css` / `semantic.css`
- **Skips anything unchanged** — compare each Figma value against what the current token already renders to, and only write real differences. Without this, gamut clipping shows up as a spurious diff on every colour.
- Opens a **branch and PR**, never writes to main. Same gate as any other change.
- Separates the diff by risk: colour changes are recolours; **spacing and type changes move every layout in every consuming app** and must be called out explicitly in the PR body as visually breaking, with a version bump implication.

### D15 — Designer-friendly Figma names, exact CSS names in code syntax

Designers see `Colour / Accent / 09`, `Spacing / 16`, `Radius / Control`. Every variable also carries its real CSS name in the WEB code syntax field, so Dev Mode shows `var(--color-accent-9)`. One variable, two labels, no ambiguity for either audience.

### D16 — Numbered steps *and* role shortcuts

Keep all 12 numbered steps, and add role-named shortcuts aliasing to them, per the purposes documented in `generate-scale.ts`:

```
Accent / Background → 03    Accent / Border → 07
Accent / Solid      → 09    Accent / Text   → 11
```

Designers who know the scale use numbers; everyone else picks by meaning. Costs a handful of variables.

### D17 — No `forced-colors` mode in Figma
Two modes: Light and Dark, both built in Phase 1 (the values already exist — it is data, not design work). High-contrast is an OS-forced accessibility fallback where the browser overrides nearly everything; designers cannot meaningfully mock it, and it would sit in every mode dropdown as a confusing third option. Code keeps handling it.

### D18 — Component token collections are per component *family*
`Component / Button` (shared by Button, IconButton, SplitButton), `Component / Input`, `Component / Badge`, and so on. A designer only sees switches relevant to what they selected. A single shared collection would become a superset where half the options are silent no-ops on any given component.

### D19 — Component vocabulary is already consistent; mirror it exactly

Investigated after it looked inconsistent. It isn't:

```
soft     tinted background, NO border      Button, Badge
subtle   tinted background, WITH border    Alert, Badge
```

Badge carrying both proves the distinction is deliberate. Select's `default` is a filled *input*, correctly not called `solid`. What looked like inconsistency is components exposing **different subsets** of a shared vocabulary — Button has no `subtle`, Alert has no `ghost`/`link`, Alert has no `accent` intent because a brand-coloured alert is meaningless.

Each component gets its real option list in Figma, including the gaps. No normalisation, no code change.

**Also corrected here:** Button has **six** intents, not five — `accent · error · success · warning · info · neutral`. `info` was missed in an earlier count and is absent from the stale cached spec. Full Button matrix is 6 × 11 × 5 = **330**.

### D20 — Foundations pages are a full reference; usage guidance comes later
Every ramp with step numbers, roles and values; the full type ramp as live specimens; spacing, radius and shadow scales at real size; the icon set; and a page explaining modes and the brand switch. This is the surface designers tune against, so it has to show real values rather than swatches alone. Do/don't usage guidance is a later pass — it is studio-voice copy and should go through Setu.

### D21 — The off-brand canvas is left for the tuning pass
The light canvas computes to `#f5f5f5`; Setu's approved Devalok light grounds are `#ffffff` / `#f8f4f5`. Build it faithfully as it is, flag it to the designers, and let re-pointing fix it — which is precisely the mechanism D13 provides. Not silently corrected during the build.

### D22 — A public Figma plugin regenerates ramps from seeds

Seed tuning has no feedback loop on its own: Figma stores a hue and a chroma but cannot compute, so changing a seed does nothing visible until the code regenerates. A designer adjusting numbers blind is not tuning.

So the seed model needs a **regenerator running inside Figma**, applying the same OKLCH maths as `src/tokens/generate-scale.ts` — change a seed, run it, all 12 steps rewrite in place.

**Distribution:** private plugin publishing requires Organization or Enterprise; Devalok is on Pro. Chosen route is **publish publicly to the Figma Community**. Consequences:

- It is brand surface — name, description and icon go through Setu before publishing
- It must be **generic** to be publishable: an OKLCH ramp generator that works on any file, not something hardcoded to our variable names
- Figma reviews public plugins (days). Designers can run it in development mode in the meantime
- Only Mudit can publish it
- Nothing private baked in — no file keys, no tokens

Lives in the repo alongside the scale generator so the maths cannot drift.

**Build order:** regenerator **before** foundations tuning begins; `figma-pull-tokens.mjs` (D14) after foundations exist, so it can be tested against real data.

### D23 — Everyone gets edit access from the start
No branching on Pro, so designers and I work in the same live file. Accepted deliberately. The collision surface is smaller than it looks: designers edit **variable values**, I create **nodes and pages**. Phase 1 is the exception, since that is when I am creating the variables themselves — coordinate during that window specifically.

### D2 — Scopes and code syntax on every variable
No `ALL_SCOPES`. WEB code syntax uses the `var(--x)` wrapper and the *actual* CSS variable name from the codebase, never one derived from the Figma name.

### D3 — Style is a variable mode; colour is a variant
Measured, not argued. Both were candidates for modes. A spike (three scenarios, live on the SPIKE page) showed the failure mode concretely: a Delete button whose intent came from a parent frame, pasted into a normal card, **silently rendered brand pink**. Its `resolvedVariableModes` flipped `7:1 → 7:0` with nothing edited.

- **Colour is semantic.** Getting it wrong means a destructive action that doesn't look destructive. It must be visible on the button itself → **variant**.
- **Style is cosmetic.** A solid button rendering as outline is obvious and harmless → **mode**, and it gains the ability to restyle a whole section in one move.

Light/dark stays a mode — there the cascade is exactly what you want.

### D4 — State axis: `Default | Hover | Pressed | Disabled | Loading`

Five values. Two corrections to earlier drafts, both found by building it:

**Loading is a state, not a boolean.** The code proves it — `renderStartSlot()` returns *either* a spinner *or* the start icon, never both, and `disabled={resolvedDisabled || (loading && !isProcessing)}` means a loading button is also disabled and renders at `--action-disabled-opacity` (0.38). A boolean can express neither the mutual exclusion nor the opacity change. As a state variant, both fall out for free: the Loading variant drops the start-icon slot's property reference entirely, so a designer who leaves "Show start icon" on **cannot** produce an icon and a spinner together. Verified: loading with the boolean on and off render byte-identically (98px, icon hidden, spinner shown).

**Focus is not modelled at all.** An earlier draft made it a boolean following M3's `Show focus indicator`. Dropped on the grounds that the browser owns `focus-visible`, the code handles it correctly, and designers don't mock focus states. It cost a node, a property and a variable, and bought nothing. (It did work — ring tracked width from 53px to 226px at a constant 2px offset, and followed pill radius once its corner radius was bound to the Shape mode — but working is not the same as worth keeping.)

Disabled stays a variant because it changes text colour, which a boolean cannot do.

### D5 — Type replaces the compound size list
Figma's guidance is explicit: *"instead of creating a single 'Style' property with values like 'Primary Large, Secondary Small', create separate 'Type' and 'Size' properties."* Our `size` axis carries `icon-sm`, `compact-md` etc. — two meanings in one value, the exact named anti-pattern. Split into:

- `Type` = `Label | Compact | Icon`
- `Size` = `xs | sm | md | lg`

Type×Size yields 11 real combinations (Compact has no `lg`).

### D6 — One Button component, no separate IconButton in Figma
Type=Icon covers icon-only. A separate Figma IconButton would duplicate it. (The *code* keeps its IconButton — see F3.)

### D7 — We publish our own editable copy of the Tabler icon library, with strokes bound in the main components

**File**: `Vst4WnV0LYfRZdC1dc7qv6` — "Tabler Icons (Copy)", owned and editable, **4,962 components**.

This is the answer, and it took three failed approaches to find. The problem it solves: Figma has no `currentColor`, so an icon can only follow its button's colour if its stroke is bound to a variable — and on a *linked* library icon that binding can only be an instance **override**, which does not survive a swap.

**What was measured (2026-08-18), in order:**

| Approach | Result |
|---|---|
| Bind strokes as instance overrides on the community library | **Fails.** Community icons have varying vector counts (1, 2, 3). Swapping a 1-vector icon for a 3-vector one leaves two vectors unbound and black. 39 of the 48 icons we use are multi-path, so this would break 81% of the set. |
| Use the icon as a **mask** over a variable-bound tint | **Fails, worse.** Survives standalone, but `isMask` is silently dropped the moment the glyph is swapped — inside a component the icon becomes a solid coloured block. Looks perfect until a designer touches it. |
| Use a built-in colour property on the library component | **Does not exist.** Tabler components expose `componentPropertyDefinitions: []`. |
| **Bind in the main components of an owned copy** | **Works.** No override exists, so nothing can be lost on swap. |

**Why the copy works where the community library does not.** The copy is *flattened*: sampled 709 components with a wide stride across all 4,962 — **every single one has exactly one vector**, zero oddities, including the complex ones (`trash`, `settings`, `search`, `bell`, `calendar-event`). All 24×24, stroke 2, round caps. Uniform structure plus write access means one binding per component, applied once, permanently.

**Build sequence — note the publish dependency, which is a human step in the middle:**

1. Phase 1 builds shilp-sutra's foundations, including the icon foreground variable.
2. **Mudit publishes shilp-sutra.** Required — cross-file variable aliasing is not possible via the plugin API; the variable must be imported from a *published* library (`figma.variables.importVariableByKeyAsync`).
3. In the Tabler copy: import that variable, then bind all 4,962 components' vector strokes to it in their main definitions.
4. **Mudit publishes the Tabler copy.**
5. Subscribe it in the shilp-sutra DS file.

From then on, any of the 4,962 icons dropped into a button follows the button's colour, and swapping between any two is safe.

**Stroke weight.** All icons are authored 24px / stroke 2, so other sizes come from scaling. Tabler keeps `viewBox="0 0 24 24"` and scales only `width`/`height`, with `strokeWidth` in viewBox units — so rendered stroke is `stroke × size/24`, and proportional scaling in Figma **exactly reproduces the code** for the tiers where the DS uses Tabler's default of 2:

```
tier   px    code stroke   renders as   Figma scaled   match
xs     14    1.5           0.875        1.167          33% heavy
sm     16    2             1.333        1.333          exact
md     18    2             1.500        1.500          exact
lg     20    2             1.667        1.667          exact
xl     24    2             2.000        2.000          exact
2xl    32    2.25          3.000        2.667          11% light
```

Four of six exact, including three of the four sizes buttons use. `xs` is 0.29px heavier than code at 14px — accepted and documented rather than fixed, since fixing it would mean a second 4,962-component set.

**Resizing does not scale stroke — set it explicitly.** Measured: an icon instance resized 24 → 14px scales its geometry (the vectors carry `SCALE` constraints already) but keeps `strokeWeight: 2`, which is far too heavy at small sizes. Each component's icon slot must therefore **set `strokeWeight` as an instance override** per size tier:

```
xs 14px → 1.167    sm 16px → 1.333    md 18px → 1.5
lg 20px → 1.667    xl 24px → 2.0      2xl 32px → 2.667
```

Normally an override would be the fragile option — but this library is uniformly **one vector per icon**, so the override always lands on the same child. Verified: set 1.5, then swap `plus → trash → settings → heart-filled` (including a fill-based icon), and it holds at 1.5 with the colour binding intact throughout. Overrides on this library are safe *because* of the flattening; they would not be on the community one.

**Verified working end to end (2026-08-18):** icons imported live from the published `Tabler Icons (for Shilp-Sutra)` library into a Button, rendering correctly across all four styles × five intents, with the glyph swappable from the full 4,962 via `preferredValues`.

**Superseded:** `figma-extract-icons.mjs` was written for the owned-curated-set approach and is no longer the plan. Keep it — it still documents the size/stroke table parsed from `icon.tsx`, and it is the fallback if the copy file is ever lost — but it is not in the build path.

### D7c — Icon inset is reproduced exactly, using an overflowing icon slot

The code keeps button padding symmetric (`px-ds-05` = 16px at md) and instead pulls icons outward with a negative margin:

```js
const iconInsetClass = {
  xs: { start:'-ml-0.5', end:'-mr-0.5' },  //  2px
  sm: { start:'-ml-1',   end:'-mr-1'   },  //  4px
  md: { start:'-ml-1.5', end:'-mr-1.5' },  //  6px
  lg: { start:'-ml-2',   end:'-mr-2'   },  //  8px
}
```

So a md button with a start icon has an effective 10px left inset, not 16.

Figma has no negative margins, and a BOOLEAN property only toggles visibility — it cannot change the parent's padding. But it doesn't need to.

**The solution: make the icon slot narrower than the glyph and let the art overflow.** The slot is a plain frame with `clipsContent = false`; the glyph sits inside at a negative local offset. The boolean toggles the **slot**, so hiding it removes the slot from the auto-layout flow entirely and padding returns to its full value.

```
slot width = iconSize − inset       glyph local x = −inset  (start)
                                    glyph local x =  0      (end, overflows right)
```

Measured against the CSS, md tier (padding 16, gap 8, icon 18, inset 6):

```
                measured   expected
icon start         10         10
icon end           28         28
label start        36         36
slot hidden →  label at 16, expected 16
```

**Exact parity, zero divergence, and no extra variants.** The slot width is conveniently constant at **12px across every tier** — 14−2, 16−4, 18−6, 20−8 all equal 12.

An earlier draft of this decision accepted a ~6px divergence, on the assumption that the glyph would have to be centred in the slot (which does break the icon↔label gap). Right-aligned and overflowing, the gap is preserved. Corrected after being challenged — worth remembering that "Figma can't do X" usually means "I haven't found the layout trick yet."

Still open: `pillPaddingClass` bumps horizontal padding one step for `shape="pill"`. Shape is a mode carrying radius; padding also varies by Size variant, so a mode can't express the delta. Either pill accepts standard padding, or padding moves into the Shape mode per size. Decide at Phase 3.

### D7d — Always regenerate the component spec before building; never trust the cached one

`.figma/components/button.json` was **stale** and would have produced a wrong Button:

```
                 cached              actual source
compound rules   25                  30          ← 5 colour combos missing
radius           rounded-ds-md/lg    rounded-control
text             text-ds-sm/md/base  text-body-sm/md/lg
```

The corrected values change the binding targets: radius binds to the **role** token `radius/control`, not a size token, and text maps to the `body/*` type roles. Run `node packages/core/scripts/figma-sync-components.mjs <name>` immediately before building each component, and read `src/ui/<name>.tsx` when anything looks surprising — **the CVA source is authoritative, the generated JSON is a convenience.**

### D7e — Prop interactions must be derived from the render code, not the CVA

The CVA gives the variant matrix. It does **not** give the rules for how props interact, and those live in the component body. For Button, read out of `button.tsx`:

| Rule | Source | Figma treatment |
|---|---|---|
| Spinner **replaces** the start icon | `renderStartSlot()` returns one or the other | Loading state drops the icon slot's property reference |
| Loading **implies disabled** | `disabled={resolvedDisabled \|\| loading}` | Loading variant carries opacity 0.38 |
| Icons dim to **90%** in solid/soft/outline | `dimIcon` | `icon/opacity` bound per Style mode |
| Spinner is **smaller than the icon** | `BUTTON_TO_SPINNER_SIZE` — sm at xs/sm/md, md at lg | 16px spinner against an 18px icon at md |
| Spinner inherits the icon inset **only if an icon was there** | `startIcon && inset.start` | Spinner slot always carries the inset; documented |
| Pill adds a padding step | `pillPaddingClass` | Open — see D7c |

**Do this audit for every component.** The CVA-derived JSON describes appearance per variant; it says nothing about which combinations are legal or what one prop does to another. Budget a read of the component body before building.

**Figma gotcha found here:** variables scoped to `OPACITY` are in **percent**, not 0–1. Setting `0.9` yields an opacity of 0.009 — a nearly invisible icon that still reads as "bound correctly" in the API. Direct `node.opacity` is 0–1. The two do not match.

### D8 — Code Connect is blocked, not deferred
Pro plan. Use `component.description` + `documentationLinks` (GitHub source path + Storybook URL) as the permanent substitute.

### D9 — Publishing is human-only
No API exists. Flag it explicitly; only Mudit can click Publish.

### D10 — A brand indirection layer, with Waybill as the second brand
Accent is currently hardwired: `--color-accent-9: var(--pink-9)`. A `Brand` collection sits between primitives and semantics so a rebrand is one mode switch:

```
Primitives   pink · red · green · amber · teal …      (raw ramps)
     ↑
Brand        modes: Devalok · Waybill
             brand/accent-1..12 → Devalok: pink   Waybill: derived blue
     ↑
Semantic     accent/9 → brand/accent-9              (was → pink/9)
     ↑
Component    btn/bg → accent/9
```

### D11 — The light canvas stays off-brand, and is flagged
DS light canvas computes to `#f5f5f5`; Setu's approved Devalok light grounds are `#ffffff` / `#f8f4f5`. Figma mirrors the code and carries the grey. Recorded as a known brand gap, not silently corrected — changing it alters every screen in every consuming app and is a separate design decision.

## The Waybill brand — what is real and what is derived

Waybill's Setu palette is ten flat brand colours with no tonal ramps. Product UI needs ~12 steps per intent. What we can and cannot honestly build:

| Intent | Anchor | OKLCH hue / chroma | Status |
|---|---|---|---|
| accent | Waybill Blue `#309EFE` | 249.7 / 0.171 | **derived** ramp, needs Waybill sign-off |
| success | Waybill Green `#24AB5C` | 151.9 / 0.161 | **derived**; Setu states green = positive/success |
| warning | Waybill Yellow `#FFC664` | 79.0 / 0.132 | **weakly inferred** — Setu's stated use is "warmth and highlight", not caution |
| error | *none* | — | **UNDEFINED — nothing red exists in the palette** |
| light ground | Waybill White `#FFF4E2` | 80.3 / 0.027 | real; pure white explicitly forbidden as a ground |
| text on light | Waybill Dark Blue `#07122B` | 263.8 / 0.053 | real |

Ramps are derived with the repo's existing `packages/core/src/tokens/generate-scale.ts` (seed hue + peak chroma → 12 steps light and dark). The maths is solved in-house; it is the *authority* that is missing.

**Two rules for the Waybill mode:**
1. The Brand collection mode is named **`Waybill (derived — unapproved)`** so nobody mistakes it for signed-off brand values.
2. `error/*` in Waybill mode renders a **visible placeholder**, not an invented red. The design system should surface the gap, not paper over it.

Also recorded, because it would bite later: Waybill Blue fails WCAG as body text on light grounds, so it cannot serve as the text-weight step (`accent-11`) of its own ramp — that step resolves toward Dark Blue.

A `gap` has been filed against Setu (`color` / `semantic`) requesting an error hue, confirmation on warning, and sign-off on the derived ramps.

## Architecture

### Variable collections

| Collection | Modes | Contents |
|---|---|---|
| Primitives / Color | Light, Dark | ~179 raw ramp steps. Scopes hidden from pickers. |
| **Brand** | Devalok, Waybill (derived — unapproved) | `brand/accent-1..12`, `brand/success-*`, `brand/warning-*`, `brand/error-*`, ground + text anchors |
| Semantic / Color | Light, Dark, forced-colors | ~112 aliases. `accent/*` now aliases Brand, not primitives. |
| Primitives / Spacing | Default | 26 |
| Primitives / Radius | Default | 8 |
| Primitives / Typography | Default | 33 |
| Component / Button | Solid, Soft, Outline, Ghost, Link | `btn/bg`, `btn/fg`, `btn/border-color`, `btn/border-width`, `btn/underline-visible` |

Seven collections; none exceeds the measured 10-mode ceiling. One component-token collection per component family that needs a style axis.

### Text styles
20 roles, each with fontSize / lineHeight / letterSpacing / weight **bound to variables** rather than frozen. Fonts: Inter and Manrope, both confirmed present (1,938 families available in this session).

**Ranade is not installed** and is not used. It is only `--font-accent` (hero moments) plus `.prose-devsabha`, so the 20 core roles are unaffected. The accent-font token is recorded with its true value so Dev Mode doesn't lie; no text style binds to it.

> Font-name trap: Inter uses `"Semi Bold"` (with a space), Manrope uses `"SemiBold"` (without). Verify via `listAvailableFontsAsync()` before any text write.

### Effect styles
8 shadows: `shadow/raised`, `raised-hover`, `floating`, `overlay`, `brand`, `error`, `success`, `warning`.

### Colour conversion
Tokens are authored in OKLCH. Figma variables need sRGB. Use the **existing Ottosson converter** in `figma-sync-tokens.mjs` (`oklchToHex`) so Figma matches the repo's own DTCG export exactly. Note it clips per-channel rather than gamut-mapping — saturated values can shift hue slightly. Accepted, because consistency with the existing DTCG output matters more than absolute fidelity.

## Button — the reference component

**220 variants** = Colour (5) × Type×Size (11) × State (4). One component set. Nothing ever needs swapping.

| Setting | Mechanism | Values |
|---|---|---|
| Colour | VARIANT | accent · error · success · warning · neutral |
| Type | VARIANT | Label · Compact · Icon |
| Size | VARIANT | xs · sm · md · lg (Compact: no lg) |
| State | VARIANT | Default · Hover · Pressed · Disabled |
| **Style** | **MODE** | Solid · Soft · Outline · Ghost · Link |
| Label | TEXT | — |
| Start icon | BOOLEAN + INSTANCE_SWAP | owned icon set; `preferredValues` scoped to the matching size (D7b) |
| End icon | BOOLEAN + INSTANCE_SWAP | same |
| Full width / Pill shape / Loading / Focus ring | BOOLEAN | — |

Only the first four multiply. Everything else is free.

**Values come from the CVA compound variants, and the mapping is not uniform.** Verified against `.figma/components/button.json`:
- `solid + accent` → bg `accent-9`, text `accent-fg`, shadow `raised`
- `solid + neutral` → bg `neutral-5`, text `surface-fg` — **breaks the step-9 pattern**
- `soft + neutral` → `surface-raised-hover` / `surface-fg-muted` — surface tokens, not neutral steps
- `ghost + *` → identical for every intent; **ghost ignores colour entirely**

Modes handle this correctly — a mode is just a different value per axis position — but the build must read the compound table rather than assume a formula.

### Phase 0 — Pre-flight

## Known risks

- **F3 is breaking and Karm consumes this library.** It also still needs the outstanding 0.56.0 TipTap peer notice. Sequence deliberately.

- **Mode cascade is a learned behaviour.** Style can be set frame-wide; someone will do it by accident. Documented on the Foundations page. Colour is deliberately immune.
- **Figma is briefly ahead of code** on the brand layer until F1 lands.
